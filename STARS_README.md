# Gaia Star Rendering — Unity VR

This document describes the Gaia DR3 star-rendering, LOD, streaming, and HDR/glare pipeline used by the Unity VR space-simulation project.

The rendering approach is independently implemented in Unity/URP and is inspired by:

> S. Schneegans, A. Kreskowski, and A. Gerndt, “Smaller than Pixels: Rendering Millions of Stars in Real-Time,” *Eurographics 2025 — Short Papers*.

The project follows the paper's central idea of treating stars as sub-pixel sources and rasterizing their contributions on the GPU. It has its own Gaia data preparation, brightness-based multi-layer LOD representation, octree hierarchy, binary formats, streaming, XR integration, and RenderGraph pipeline. It is not the CosmoScout VR implementation.

---

## 1. System overview

The current rendering system has three closely connected parts:

1. **LOD selection and streaming** — selects and loads the star nodes needed by the current view.
2. **Live star rasterization** — renders selected stars directly from GPU star buffers.
3. **HDR composition and glare** — reconstructs the star image, generates glare, and composites the result with the camera image.

The data preparation and runtime flow is:

```text
Gaia DR3
    ↓
offline preprocessing
    ↓
DataRaw/Gaia/processed/*.bin
    ↓
3_build_stars_lod.py
    ├── scans valid star records and spatial bounds
    ├── sorts stars by brightness field (ascending absolute G magnitude)
    ├── creates nested top-N star layers
    └── builds an octree for each layer
            ↓
Data/Gaia/lod/
    ├── manifest.json
    └── layer_<top-N>/
        ├── metadata.bin
        ├── summary.json
        ├── particles/
        └── source_ids/
            ↓
    StarsLODLoader
    ├── frustum culling
    ├── LOD selection
    ├── asynchronous loading
    └── GPU GraphicsBuffers
            ↓
     GaiaStarRasterizer
            ↓
  GaiaStarRasterizer.compute
            ↓
  fixed-point star accumulation
            ↓
  GaiaStarComposite.shader
            ↓
          Star HDR
            ↓
       glare pyramid
            ↓
  GaiaStarFinalComposite.shader
            ↓
       final camera image
```

Stars are not represented by individual Unity GameObjects, meshes, or billboard objects.

## 2. Gaia data and preprocessing

The project uses **Gaia Data Release 3 (DR3)** as a local offline stellar catalogue. Unity does not download Gaia data during runtime.

The offline preprocessing stage produces binary records in:

```text
DataRaw/Gaia/processed/
```

The current LOD builder expects each processed record to be **77 bytes** and contain the following fields: source ID, XYZ position, G magnitude, BP−RP colour, effective temperature, surface gravity, metallicity, radius, extinction-related values, mass, age, evolutionary stage, and flags. The builder reads these records directly; it does not download or preprocess the original Gaia archive itself.

### Original catalogue index

The original Gaia chunk/index organization uses HEALPix level 6 and radial-distance shells:

```text
0–100 pc
100–250 pc
250–500 pc
500–1000 pc
1000–2000 pc
2000–5000 pc
5000–10000 pc
10000–20000 pc
20000–40000 pc
40000+ pc
```

This organization can support data locality and preprocessing. The current MS LOD output is a separate representation generated by `3_build_stars_lod.py`; the per-layer `metadata.bin` files and particle files described below are the files used for the new LOD layout. An `index.bin`, if retained in the data package, should not be confused with the generated MS LOD metadata.

### Brightness-sorted layers

`Tools/Gaia/3_build_stars_lod.py` reads all valid processed records, sorts them by the `g` field in ascending order, and creates nested **top-N** layers. The builder's documented convention is that `g` contains **absolute G magnitude**, where lower values are brighter. Each layer contains the brightest prefix of the sorted catalogue; larger layers include the stars from smaller layers plus additional, fainter stars.

The current defaults are:

```text
FIRST_LAYER_STAR_COUNT = 100
LAYER_STAR_MULTIPLIER  = 2.0
MAX_STARS_PER_NODE     = 2,000
MAX_OCTREE_DEPTH       = 20
READ_BLOCK_STARS       = 1,000,000
```

The star count approximately doubles from layer to layer. The final layer is capped at the exact number of valid stars, so it may not be a power-of-two multiple. For example, if the processed input contains 618,431 valid stars, the generated layer counts end with 409,600 and then 618,431.

**Layer indices are zero-based.** The first layer has index `0`, the second has index `1`, and so on. This index is stored in the manifest and summary metadata. The directory name uses the requested star count instead of the index; for example, `layer_409600` is not a layer index of 409600.

The builder relies on the preprocessing stage to provide the intended catalogue selection. It discards records with non-finite XYZ coordinates or a non-finite `g` value, but it does not apply a fixed dust-box cutoff or a separate maximum-distance filter itself.

### Spatial bounds and coordinate convention

The builder calculates spatial bounds from all valid input records, then constructs a **cubic root volume** large enough to contain the full XYZ range. This means the exact root bounds depend on the current processed input. If the catalogue must be clipped to the project's dust box, apply that selection during preprocessing before running the LOD builder.

The project's coordinate convention is Sun-centred, with the galactic plane mapped to Unity's XZ plane and Unity Y pointing up. The dust volume has previously been configured with approximate half-extents of X ±1010 pc, Y ±410 pc, and Z ±1010 pc. These are dust-volume bounds, not hard-coded bounds in the current LOD builder.

### Generated output layout

A successful build produces this directory structure:

```text
Data/Gaia/lod/
├── manifest.json
├── layer_100/
│   ├── metadata.bin
│   ├── summary.json
│   ├── particles/
│   │   └── particles_XXXXXXXX.bin
│   └── source_ids/
│       └── source_ids_XXXXXXXX.bin
├── layer_200/
│   └── ...
└── layer_<final-top-N>/
    └── ...
```

Each layer has its own octree metadata and leaf particle files. `manifest.json` lists the available layers and their zero-based indices, star counts, node counts, and other build settings. Each layer's `summary.json` records layer information and node-depth statistics.

The particle record is **36 bytes** and contains XYZ position, G magnitude, BP−RP, effective temperature, mass, age, and evolutionary stage. The source IDs are written separately as 64-bit unsigned integers, so they can be associated with each leaf's particle records without increasing the runtime rendering record size.

The builder constructs the new data in `Data/Gaia/lod_building` and replaces `Data/Gaia/lod` only after the layers and manifest have been written successfully. It uses `Data/Gaia/lod_previous` as a temporary backup during replacement. If Windows reports `PermissionError` during folder replacement, a process such as Unity or another file viewer may be holding a file or directory open; close programs accessing these folders and rerun the builder.

## 3. LOD hierarchy and streaming

### `StarsLODLoader`

This is the active runtime LOD and star-data loader. It reads the generated layer metadata and streams the nodes required by the current view. Check the loader's serialized fields and project settings for the current runtime defaults; those values may change during tuning.

Each layer contains an octree of spatially bounded nodes. The builder splits a node when it contains more than `MAX_STARS_PER_NODE` stars. Internal nodes contain child links but no particle records; only leaves store stars. The builder verifies that every star in a layer is assigned to exactly one leaf and that no leaf exceeds the configured limit. If the limit cannot be met by `MAX_OCTREE_DEPTH`, the build fails rather than silently creating an oversized leaf.

Runtime LOD selection is based on view-dependent node size / angular coverage rather than distance alone. Conceptually:

```text
camera
  ↓
frustum culling
  ↓
node screen-size / LOD test
  ├── sufficient detail → keep selected node
  └── more detail needed → recurse into children
```

The precise threshold, selection rules, transition behaviour, and supported layer range are defined by the current loader implementation and settings. Do not infer these values from the Python builder defaults alone.

### Streaming

After selecting the desired nodes, the loader compares them with the currently resident set:

```text
Desired nodes
    ├── already resident → keep
    ├── missing           → load asynchronously
    └── no longer needed  → unload
```

Particle files are read asynchronously and uploaded to `GraphicsBuffer` objects. Limits on concurrent loads and resident data determine CPU/GPU memory usage. Only the selected nodes need to be resident; the complete catalogue and all generated layer files remain on disk.

## 4. Live star rendering

### `GaiaStarRasterizer.cs`

Owns the screen-sized GPU accumulation buffers and provides loaded star buffers to the RenderGraph renderer.

### `GaiaStarRasterizer.compute`

The compute shader processes approximately one star per GPU thread:

```text
star
  ↓
project to screen
  ↓
find sub-pixel position
  ↓
calculate brightness contribution
  ↓
distribute to 2×2 neighbouring pixels
  ↓
atomic fixed-point accumulation
```

The 2×2 distribution reduces pixel popping and gives smoother star motion when stars move across pixel boundaries.

The accumulation uses integer `uint` buffers with a fixed-point scale, allowing many star contributions to be combined with atomic operations.

The runtime GPU star record is **20 bytes**:

```text
float3 position
float  magnitude
float  bpRp
```

The current colour model derives an approximate star colour from BP−RP.

## 5. HDR composition and glare

### `GaiaStarComposite.shader`

Reconstructs the live star accumulation into an HDR star image:

```text
live star accumulation
          ↓
        StarHDR
```

### Glare pipeline

The HDR star image is processed through a multi-resolution glare pyramid. The current design uses five progressively smaller levels, reaching approximately 1/32 of the original resolution. Each level is downsampled and blurred with separable horizontal/vertical Gaussian passes.

### `GaiaStarFinalComposite.shader`

The final stage combines:

```text
camera image
+ sharp StarHDR
+ multi-resolution glare
```

The result is written back as the final camera image.

---

## 6. XR / VR

The rendering path is designed for XR and supports mono and stereo cameras.

For stereo rendering, the live compute rasterizer receives independent left/right view-projection matrices. Each eye's stars are projected using that eye's view, preserving the correct stereo view.

## 7. RenderGraph structure

`GaiaStarRenderFeature.cs` connects the GPU stages through Unity URP RenderGraph:

```text
loaded star GraphicsBuffers
        ↓
compute accumulation
        ↓
star HDR reconstruction
        ↓
glare prefilter / pyramid
        ↓
final composite
```

Intermediate HDR textures are tracked as RenderGraph resources. Resources shared between separate passes use the explicit RenderGraph global-texture mechanism rather than relying on unrestricted global command-buffer state.

## 8. Memory model

The system separates catalogue storage, resident LOD data, and screen-space rendering:

```text
Full Gaia catalogue / processed files
              ↓
        local files on disk
              ↓
     generated nested LOD layers
              ↓
         selected octree nodes
              ↓
      CPU / GPU resident buffers
              ↓
    screen-sized accumulation
              ↓
       HDR star image + glare
```

This lets the runtime use a large local stellar catalogue without loading the entire catalogue into CPU/GPU memory or continuously representing stars as individual scene objects. Runtime memory usage depends on the selected layer and nodes, streaming concurrency, GPU buffer sizes, and screen-space render targets.

## 9. Main runtime and build components

| Component | Responsibility |
|---|---|
| `3_build_stars_lod.py` | Builds brightness-sorted nested top-N layers and an octree for every layer. |
| `StarsLODLoader` | Active runtime LOD selection, node streaming, and GPU star buffers. |
| `GaiaStarBufferProvider` | Interface between star-data providers and rendering, if used by the current project revision. |
| `GaiaStarRasterizer` | Owns live accumulation buffers and renderer settings. |
| `GaiaStarRenderFeature` | URP/RenderGraph integration for the star-rendering pipeline. |
| `GaiaStarFilter` | Optional filtering of stars by supported stellar properties. |
| `GaiaClusterFilter` | Optional filtering of cluster data. |

The older `GaiaStarLoader.cs` architecture is not the active path for the generated multi-layer octree catalogue. If legacy index-reading classes remain in the project, distinguish their role from `StarsLODLoader` and the `Data/Gaia/lod/layer_*/` files.

- tighter integration with exposure and tone mapping;
